# Component model

A component definition declares its type, palette metadata, icon identifier, visual/nonvisual role, child support, default event, fixed-layout fallback bounds, structural layout controls, property definitions, and event definitions. Palette, Inspector, naming, model creation, generation, and validation consume this registry. Browser and React adapters remain small type-keyed projections because they construct different host objects.

Each `ComponentNode` contains an immutable ID, registered type, unique TypeScript-safe name, parent ID, required v2 `layout`, fixed-layout fallback bounds, property bag, event bindings, an optional reusable `styleId`, and ordered child IDs. The layout has a `container` rule set for direct children and an `item` rule set for the node's participation in its parent. Component names also may not collide with inherited `WebPage` runtime members because generated fields live on that subclass. Visual ordering follows the parent's child list. Nonvisual definitions use the same persistent nodes and command/history path, but the Designer shows them in its dedicated tray and excludes them from canvas geometry. Their runtime constructors receive the node's stable `id` and current `name`, so nonvisual services preserve identity without requiring a DOM element.

Reusable visual styles live at project level as `ComponentStyleModel` records. A style targets exactly one registered component type and stores structured visual properties for base, hover, focus, active, and disabled states. New projects seed the editable Aurora library: one `preset: "default"` style for every visual MVP component, excluding nonvisual services. A default style retains its component type and preset identity and cannot be removed, but its name and visual properties remain fully editable. The project-model factory binds the page root and every newly added page to the page default; the IDE binds each newly inserted visual node to its compatible default before the command enters history. Transitions, supported built-in animations, and safe two-color linear `textGradient`, `backgroundGradient`, and `borderGradient` values are ordinary typed properties, so they can be configured per state without exposing class or code fields. Each gradient is mutually exclusive with its same-target solid color. Text gradients are projected onto stable caption descendants of labels, buttons, and checkbox captions, preserving the root component's background. Border gradients are projected as a transparent solid border plus padding-box and border-box background layers, so the browser clips them to the same `borderRadius` as the component instead of relying on `border-image`. The metadata catalog is the shared source for editor controls, validation, defaults, applicability, and Tailwind candidate generation. The aggregate validator rejects missing or type-incompatible references. The page-only validator deliberately retains unresolved references so a `.wrpage` can be loaded before its manifest. Style removal is safe-by-default: for user-created styles, the pure removal operation clears every matching `styleId` across all project pages.

When a component has a selected style, that style owns its initial paint properties (background, foreground, border, and image fit). Structural layout remains model-owned: `layout.container` describes child flow or anchoring, `layout.item` describes sizing, constraints, and anchors, and `bounds` supplies the fixed-mode fallback. The runtime applies structural declarations with inline `!important` precedence, so reusable visual style utilities cannot move, resize, or change the display mode of an instance. Runtime code can still change typed paint properties dynamically.

The Registry exposes structural controls with the `layout-container` and `layout-item` property sources. `WebPage` and `WebPanel` expose container controls; visual components expose item controls. These controls edit persisted layout fields and are intentionally separate from typed runtime property accessors, which continue to describe executable component APIs.

The live Designer preserves geometry and selection wrappers around nested nodes. Its state preview merges the base properties with the selected state before generating unprefixed preview candidates, while the generated application uses real pseudo-state variants. The preview stylesheet includes both forms; production output keeps only real variants.

Property definitions select inspector editors (`string`, `string-list`, `number`, `boolean`, `enum`, `color`, `component`, or a component-specific structured editor such as `api-client-config` and `data-grid-config`). Defaults are materialized when a component is created, which keeps saved projects predictable. Properties registered for the MVP components have corresponding typed runtime accessors, making the Inspector contract available through TypeScript without making React instances the source of truth.

`WebApiClient` is a nonvisual definition with a mutable `baseUrl` and a versioned `apiClientConfig` property, in addition to its readonly `id` and `name`. The configuration contains named operations with stable IDs, TypeScript-safe operation names, an arbitrary HTTP method, path, enabled headers and query parameters, request-body kind/content, credentials, and client or operation timeout. A Registry-declared designer action opens its dedicated API Client tester from the nonvisual tray double-click or the Inspector action; the tester sends the same direct browser request that the generated application will send, so normal API CORS rules apply.

Its Inspector also exposes `OnRequest`, `OnSuccess`, `OnError`, and `OnComplete`. These lifecycle events are emitted only for named `execute` operations: a newly created handler receives the API Client as sender and an `event: CustomEvent<WebApiOperationEventDetail>` whose detail contains the configured operation and its loading, success, or error state. `OnComplete` follows either terminal result.

Testing may infer a response-contract tree. The tree records stable node IDs, JSON Pointer paths, node kind (`field`, `object`, or `list`), nullable state, and a preselected scalar type. It is deliberately a contract rather than a response cache: sampled response bodies are never persisted in the Project Model. Those stable IDs and list/object/field definitions are the binding surface for future data-aware components. The language generator turns saved contracts into typed `WebApiClient<TOutputs>` fields, while legacy API Client nodes without the optional configuration normalize to one default request and remain readable in v2 projects.

`WebDataGrid` is a visual, styled component with one `dataGridConfig` property. Its registry-declared configurator opens a dedicated, transactional modal from the Inspector or a Designer double-click; Cancel and Escape discard the modal draft, while Save creates one property-history entry. The configuration stores the selected `WebApiClient` ID, selected operation ID, a JSON Pointer to a response list (including nested lists), header/footer visibility and stickiness, row sizing, cell presentation options, and an ordered column definition. Every column binds a JSON Pointer relative to the repeated list item, renders it as text, image, button, or checkbox, and can use a fixed pixel width or a dynamic minimum/maximum/flex track alongside independently aligned header and cell content. The browser runtime and Designer use the same CSS Grid track projection, so fixed and dynamic columns genuinely coexist; rows can have a fixed clipped height or grow with wrapped content within configured limits. The Inspector only offers lists and fields from the saved response contract. The grid subscribes to its selected API Client but never executes it: authored page code calls `this.ApiClient.execute(...)`, then the grid renders the latest successful operation result. `OnCellClick` supplies the row index, source row, and column metadata to authored code.

`WebDataGrid` styles additionally expose base-state-only `Data Grid Lines`, `Data Grid Header`, and `Data Grid Footer` groups. A shared grid style can independently show or hide horizontal and vertical lines and configure each axis's color, width, and border style. An unset line-visibility style falls back to the per-grid line setting in `dataGridConfig`; a saved style value overrides it for every grid using that style. Header and footer are configured separately with their own background and text colors, separator border color/width/style, height, horizontal and vertical padding, and font weight. These component-only style properties are projected by the same browser-safe CSS used by the Designer and generated runtime.

Every non-root node, whether visual or nonvisual, is generated as `public readonly Name: Type` in both the implementation base class and its editor declaration. The page root is represented by `this`, including root event bindings, and is not emitted as another field. In authored code the canonical expression is `this.Name`. The editor offers Delphi-like completion entries using the shorter `Name` label and inserts `this.Name`, after which native TypeScript completion provides the registered runtime properties.

Changing a component's `Name` updates the Project Model and regenerates its field and typings. It does not perform an implicit rewrite of user-authored TypeScript; references to the previous name remain in the source and are reported by TypeScript until explicitly changed.

Visual components share `@webrad/runtime/visual`: property readers, class names, common style projection, and component CSS. React only maps the registered component type to the appropriate DOM element; selection, hit testing, and keyboard behavior remain in the separate design overlay.

Containers own children and `WebPanel` is the first child-capable component. In version 2, a fixed container uses child `bounds`; an align-to-parent container uses item anchors and insets; row and column containers use item sizing, constraints, grow/shrink, gap, wrapping, and alignment. There is no page-level layout mode. Component IDs remain unchanged as a node moves between these layout modes.
