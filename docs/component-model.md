# Component model

`WebMenu` is a registered visual navigation component with a transactional
tree/appearance/profile/mobile editor and a typed browser runtime. Its saved
`configuration` is shared by Designer, Preview and export. Reusable project
templates compose registered components and supply initial TypeScript source for
a new definition, preserving existing authored files. See [Menu](menu.md).

`WebTextArea` exposes **Behavior → Spell Check** in the Inspector (`props.spellCheck`, boolean, default `true`). Disabling it sets the native textarea's `spellcheck` to `false` in Designer and generated browser applications, suppressing the browser's spelling marks. Existing projects that omit the property retain spell checking. The public runtime property `TextArea1.spellCheck` (also `this.TextArea1.spellCheck`) reads or updates the setting as a boolean; for example, `this.TextArea1.spellCheck = false;`. Runtime assignments are transient and do not change the saved Project Model.

Static ComboBox options use paired `items` labels and `values` keys. The Registry declares separate Items and Values actions which open the same simple multiline modal, focusing the requested field. Each value corresponds to the label on the same line, while an empty Values list uses the labels as keys. Both arrays are saved in one undoable Designer transaction; cancelled drafts never enter the Project Model. The public `values` getter/setter is typed in the browser runtime and Monaco, and the native select carries the same keys in Designer and Preview.

`WebComboBox` supports static `items` and an optional model-owned `comboBoxConfig` API binding. Its registry action opens a transactional configurator with API Client, operation, response-list, display-field and key-field choices from the saved response contract. Save creates one undoable property command; Cancel and Escape discard the draft. Bound ComboBoxes subscribe to the local client instance and project its operation results into native select options without initiating requests. The public `comboBoxConfig` and `bindApiClient(WebApiClient | null)` APIs are typed in the runtime and Monaco. `value` returns the key as a string, `items` exposes the displayed labels and values, and `OnChange` retains its normal contract. Generated page and reusable classes initialize the binding and release subscriptions when disposed. Every reusable placement binds its own local API Client.

`WebImage` automatically minifies still PNG, JPEG, and WebP images with a shared browser-only area resampler. Each output pixel averages the covered source area with premultiplied alpha, avoiding transparent-edge halos; it does not apply a display blur. The Designer, Styles samples, compiled Preview, and exports use the same binding. The target bitmap accounts for the content box, `objectFit`, Designer zoom, and device pixel density, and is regenerated after source or size changes. Native-size and enlarged images retain their original rendering. `objectFit: 'none'`, SVG, GIF, animated PNG/WebP, other formats, and authored `srcset` remain native. Cross-origin images need readable CORS responses; fetch/decoder/canvas/CSP failures preserve native display.

The source asset and typed `WebImage.src`, `alt`, and `objectFit` APIs stay intact. A temporary SVG blob wraps the reduced PNG bitmap with the exact original intrinsic dimensions and aspect ratio, including rectangular images with rounded output dimensions. It is selected through `srcset` with the original width descriptor and `sizes`. No bitmap or rendering preference is persisted in the Project Model. The binding coalesces updates, ignores stale work, bounds sources to 20 MiB and 16 megapixels and outputs to 4 megapixels, and releases requests, observers, timers, density listeners, and URLs on React unmount or runtime disposal.

Every built-in visual component exposes **Margin**, **Margin top**, **Margin right**, **Margin bottom**, and **Margin left** in the Inspector, including Page, Popup, and reusable placements. The numeric `props.margin` provides outer spacing on all four sides in pixels; `props.marginTop`, `props.marginRight`, `props.marginBottom`, and `props.marginLeft` override individual sides, including zero. Missing sides display the shared margin or zero without materializing that fallback in the model. Missing properties preserve shared style margins. Code uses typed `Component.marginTop` or `this.Component.marginTop` access (the page root uses `this.marginTop`), with equivalent APIs for the other sides. Runtime assignment to `margin` resets all four sides; assignment to a side changes only that side. Values must be finite; fractional and negative margins are supported. Row and column containers include margins between items; fixed layouts retain authored coordinates and apply CSS margin offsets. Margin does not replace container padding or gap. The Designer applies child margins to the structural layout host and the runtime applies them to the visual element.

A component definition declares its type, palette metadata, icon identifier, browser-DOM ownership (`visual`), optional Designer presentation, child support, default event, fixed-layout fallback bounds, structural layout controls, property definitions, and event definitions. Event metadata may also declare its runtime detail type and the detail fields that the authored-handler generator introduces as local constants. Palette, Inspector, naming, model creation, generation, and validation consume this registry. Browser and React adapters remain small type-keyed projections because they construct different host objects.

Inspector sections come from Registry metadata: property `category` selects the section and optional `inspectorGroup` creates a subgroup. Every component uses the same compact two-column rows, with the property name on the left and its editor on the right, including properties marked `editorLayout: "compact"`, shared styles, and events. Standard controls are 24 px high; long names wrap within their column, and multiline editors retain room for multiple lines. All built-in components share the same layout-property organization: **Size & position**, **Spacing**, **Responsive size**, **Anchors & offsets**, and **Children layout** where applicable. Property search matches names, labels, sections, and subgroups, including mixed selections. Search opens matching sections temporarily and restores their collapsed state when cleared. This presentation does not modify saved properties or the runtime API.

Each flow item exposes **Item alignment** under **Responsive size / Alignment**, persisted as `layout.item.alignSelf`. Values are `auto`, `start`, `center`, `end`, and `stretch`; `auto` keeps the existing sizing/alignment behavior. An explicit value overrides the parent's cross-axis alignment for that item alone: vertical in a row and horizontal in a column. Fixed and anchored layouts use their position/anchor rules. **Children layout / Default alignment** remains the container's fallback for children without an individual override. Existing fixed dimensions and min/max limits still apply; `stretch` fills an automatic cross-axis size. A responsive cross-axis `stretch` dimension continues to request stretching while alignment is `auto`. All visual runtime classes also expose the typed `Component.alignSelf` and `this.Component.alignSelf` API. Runtime assignment updates CSS immediately without changing saved project state; assigning `auto` uses CSS inheritance from the parent.

Each `ComponentNode` contains an immutable ID, registered type, unique TypeScript-safe name, parent ID, required v2 `layout`, fixed-layout fallback bounds, property bag, event bindings, an optional reusable `styleId`, and ordered child IDs. The layout has a `container` rule set for direct children and an `item` rule set for the node's participation in its parent. Component names also may not collide with inherited `WebPage` runtime members because generated fields live on that subclass. Visual ordering follows the parent's child list. DOM-less nonvisual definitions use the same persistent nodes and command/history path, but the Designer shows them in its dedicated tray and excludes them from canvas geometry. Their runtime constructors receive the node's stable `id` and current `name`, so nonvisual services preserve identity without requiring a page-layout DOM element. A visual definition normally appears on the Designer canvas, but may explicitly set `designerPresentation: "tray"`: `WebPopup` uses that presentation while remaining a DOM-backed, normally styled browser component.

`WebReusableElement` is a childless visual placement wrapper rather than a copied component tree. Its required stable `reusableElementId` selects a manifest-owned definition; its normal v2 item layout belongs to the placement, and its `placement`, viewport anchors, and layer can instead make that placement floating. The wrapper remains addressable from its host page, but definition descendants and nonvisual services remain encapsulated in the reusable's generated/user class. Every placement receives that class independently, so its registered events and mutable state are isolated just as page component events and state are.

Reusable visual styles live at project level as `ComponentStyleModel` records. A style targets exactly one registered visual component type and stores structured visual properties for base, hover, focus, active, and disabled states. New projects seed the editable Aurora library with one `preset: "default"` style for each standard visual rendering component, including the `WebPopup` browser dialog, excluding DOM-less nonvisual services and the transparent `WebReusableElement` placement wrapper; the referenced definition owns the usual appearance. A default style retains its component type and preset identity and cannot be removed, but its name and visual properties remain fully editable. The project-model factory binds the page root and every newly added page to the page default; the IDE binds each newly inserted visual node, whether presented on the canvas or in the tray, to its compatible default before the command enters history. Transitions, supported built-in animations, and safe two-color linear `textGradient`, `backgroundGradient`, and `borderGradient` values are ordinary typed properties, so they can be configured per state without exposing class or code fields. Each gradient is mutually exclusive with its same-target solid color. Text gradients are projected onto stable caption descendants of labels, buttons, and checkbox captions, preserving the root component's background. Border gradients are projected as a transparent solid border plus padding-box and border-box background layers, so the browser clips them to the same `borderRadius` as the component instead of relying on `border-image`. The metadata catalog is the shared source for editor controls, validation, defaults, applicability, and Tailwind candidate generation. The aggregate validator rejects missing or type-incompatible references. The page-only validator deliberately retains unresolved references so a `.wrpage` can be loaded before its manifest. Style removal is safe-by-default: for user-created styles, the pure removal operation clears every matching `styleId` across all project pages and reusable definitions.

When a component has a selected style, that style owns its initial paint properties (background, foreground, border, and image fit). Structural layout remains model-owned: `layout.container` describes child flow or anchoring, `layout.item` describes sizing, constraints, and anchors, and `bounds` supplies the fixed-mode fallback. The runtime applies structural declarations with inline `!important` precedence, so reusable visual style utilities cannot move, resize, or change the display mode of an instance. Runtime code can still change typed paint properties dynamically.

Every visual component also has `visible` and `collapseWhenHidden` behavior properties. `collapseWhenHidden` defaults to `true`: when `visible` is false, the component is removed from layout and does not reserve space. Set it to `false` to hide the component while retaining its layout area. The Designer and generated browser runtime use the same projection.

The Registry exposes structural controls with the `layout-container` and `layout-item` property sources. `WebPage` and `WebPanel` expose container controls; visual components expose item controls. These controls edit persisted layout fields and are intentionally separate from typed runtime property accessors, which continue to describe executable component APIs.

The live Designer preserves geometry and selection wrappers around nested nodes. Its state preview merges the base properties with the selected state before generating unprefixed preview candidates, while the generated application uses real pseudo-state variants. The preview stylesheet includes both forms; production output keeps only real variants.

Property definitions select inspector editors (`string`, `string-list`, `number`, `boolean`, `enum`, `color`, `component`, or a component-specific structured editor such as `api-client-config` and `data-grid-config`). A property may declare static `readOnly` metadata or a pure `readOnlyWhen(props)` design-time predicate over the saved property bag. The Inspector resolves those registry rules generically and prevents editing a shared property when any selected component declares it read-only. This keeps the API Client's `baseUrl` fixed in the Inspector when its configuration binds to RestGo, without an API-specific condition in the IDE. Defaults are materialized when a component is created, which keeps saved projects predictable. Properties registered for the MVP components have corresponding typed runtime accessors, making the Inspector contract available through TypeScript without making React instances the source of truth.

`WebApiClient` is a nonvisual definition with a versioned `apiClientConfig` property and readonly `id` and `name`. Its custom connection has a mutable `baseUrl`; its optional `restgo-session` connection fixes that URL to the project RestGo integration, appends only the operation endpoint beneath the configured prefix (including reverse-proxy paths), and obtains the authenticated user's current JWT for `Authorization: Bearer <JWT>` on each request. It requires an authenticated session and does not fall back to the integration's application token. Attempts to replace the bound base URL or endpoint origin fail explicitly. Saved enabled `Authorization` headers are rejected in bound mode, and runtime request headers always receive the current session's Bearer JWT. The configuration contains named operations with stable IDs, TypeScript-safe operation names, an arbitrary valid HTTP method token, path, enabled headers and query parameters, request-body kind/content, credentials, and client or operation timeout. The tester lists GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS, CONNECT, and TRACE and accepts custom methods; browser Fetch cannot send CONNECT, TRACE, or TRACK, so those report an explicit limitation. Request bodies support JSON, raw text, URL-encoded forms, and multipart forms with persisted text fields; programmatic `FormData` supplies runtime-only files. A Registry-declared designer action opens its dedicated API Client tester from the nonvisual tray double-click or the Inspector action; the tester sends direct browser requests, so normal API CORS rules apply. The IDE's temporary test JWT is kept only in memory and never becomes part of the saved project.

Its Inspector also exposes `OnRequest`, `OnSuccess`, `OnError`, and `OnComplete`. These lifecycle events are emitted only for named `execute` operations: a newly created handler receives the API Client as sender and an `event: CustomEvent<WebApiOperationEventDetail>` whose detail contains the configured operation and its loading, success, or error state. `OnComplete` follows either terminal result.

The native RestGO SDK is a project-level browser service configured from `settings.restGo`. Authored component event handlers access its typed shared `RestGO` client for authentication, Storage, and published dynamic endpoints. Its session and request results are transient runtime data, while the instance connection and persistence policy belong to the saved Project Model.

Testing may infer a response-contract tree. The tree records stable node IDs, JSON Pointer paths, node kind (`field`, `object`, or `list`), nullable state, and a preselected scalar type. It is deliberately a contract rather than a response cache: sampled response bodies are never persisted in the Project Model. Those stable IDs and list/object/field definitions are the binding surface for future data-aware components. The language generator turns saved contracts into typed `WebApiClient<TOutputs>` fields, while legacy API Client nodes without the optional configuration normalize to one default request and remain readable in v2 projects.

`WebDataGrid` is a visual, styled component with one `dataGridConfig` property. Its registry-declared configurator opens a dedicated, transactional modal from the Inspector or a Designer double-click; Cancel and Escape discard the modal draft, while Save creates one property-history entry. The configuration stores the selected `WebApiClient` ID, selected operation ID, a JSON Pointer to a response list (including nested lists), header/footer visibility and stickiness, row sizing, cell presentation options, and an ordered column definition. Every column can bind a JSON Pointer relative to the repeated list item or leave its field unselected, renders as text, image, button, or checkbox, and can use a fixed pixel width or a dynamic minimum/maximum/flex track alongside independently aligned header and cell content. Button and checkbox columns additionally expose a fixed caption: buttons use it instead of the bound row value when it is non-empty, while checkboxes render it beside the boolean control. A button column can also select an optional icon from the same closed local catalogue as `WebButton`; combining its nullable icon with the optional caption allows caption-only, icon-only, or caption-and-icon cells. The browser runtime and Designer use the same CSS Grid track projection, so fixed and dynamic columns genuinely coexist; rows can have a fixed clipped height or grow with wrapped content within configured limits. The Inspector only offers lists and fields from the saved response contract. The grid subscribes to its selected API Client but never executes it: authored page code calls `this.ApiClient.execute(...)`, then the grid renders the latest successful operation result. `OnCellClick` supplies zero-based row and column indexes, the source row, column metadata, the clicked field value, and `getValue(nameOrPointer)` for reading any other value from that same row by a simple property name such as `url` or a JSON Pointer such as `/customer/id`. A newly created handler also starts with `const { column, rowIndex, columnIndex, value, getValue } = event.detail;`.

`WebPopup` is a visual, DOM-backed dialog with `designerPresentation: "tray"`. Its node is inserted and selected from the Designer's nonvisual tray and has no Designer canvas geometry, but the compiler serializes it through the ordinary visual browser DOM model and generated page or reusable classes expose it as typed `this.PopupName`. The runtime wraps a native `<dialog>` element: `show()` opens it (modally by default), while `hide()` or `close()` closes it. The selected `WebPopup` style is resolved into the same static CSS and class pipeline used by other visual components and applied to the dialog surface. A modal dialog enters the browser's top layer when available, while normal component disposal removes its listeners with the rest of its generated page or reusable scope.

`WebDataGrid` configuration is a transactional draft: Save commits one configuration through the Project Model, while Cancel or Escape discards edits. Native project commands are blocked while the dialog is open; theme switching remains available. Its dialog groups header, footer, content, and line options; sticky controls are available only while their corresponding row is shown, and hiding a row preserves its settings for later use. Number fields allow temporary clearing while editing; leaving a non-null field empty restores its last valid value, while an empty optional maximum means no limit. Column cards show their position, header, cell type, and width rule; reordering preserves their stable IDs. The browser grid reports row counts and indices consistently across visible headers, data or empty-state rows, and footers.

`WebDataGrid` styles additionally expose the base-state-only `Data Grid Lines`, `Data Grid Header`, `Data Grid Footer`, `Data Grid Button`, and `Data Grid Checkbox` groups. A shared grid style can independently show or hide horizontal and vertical lines and configure each axis's color, width, and border style. An unset line-visibility style falls back to the per-grid line setting in `dataGridConfig`; a saved style value overrides it for every grid using that style. Header and footer are configured separately with their own background and text colors, separator border color/width/style, height, horizontal and vertical padding, and font weight. Cell buttons have independent background, text, border, radius, padding, font-weight, content-mode, icon-position, icon-size, and icon-color controls. The icon presentation applies to all button cells: icon-only captions use screen-reader-only text, preserving each button's accessible name, and SVG sizing happens within a fixed, centered 16px flex slot so it cannot resize or vertically offset the button. Cell checkboxes have independent accent-color and size controls plus caption color, font weight, and spacing. These component-only style properties are projected by the same browser-safe CSS used by the Designer and generated runtime.

Every component, visual or nonvisual, exposes a real runtime class with a typed programming API. Every non-root node is generated as `public readonly Name: Type` in both the implementation base class and its editor declaration. The page root is represented by `this`, including root event bindings, and is not emitted as another field. Authored instance code supports both `Name.member` and `this.Name.member`, with native TypeScript completion, hover, signatures, and diagnostics. Bare names are resolved through the shared AST and symbol-based language contract; lexical bindings retain precedence and each reusable placement retains its own instance. New components must export their runtime API, update editor declarations and generated runtime sources, and validate their typed API and compiled execution as well as their Designer representation.

Changing a component's `Name` updates the Project Model and regenerates its field and typings. It does not perform an implicit rewrite of user-authored TypeScript; references to the previous name remain in the source and are reported by TypeScript until explicitly changed.

The Styles workspace defaults to an Essential view curated by each visual definition's optional `styleEditor.essentialProperties` Registry metadata. Configured properties remain visible in that view even when they are advanced. All properties exposes the complete applicable catalog, and Configured shows only the current state's overrides. Search always spans the complete component/state catalog and opens matching groups. The Designer groups appearance, text, spacing, component-specific surfaces, layout/size, motion, and interaction without changing persisted property names or supported values; Data Grid surfaces appear as Lines, Header, Footer, Cell button, and Cell checkbox. Missing curation metadata falls back to the complete catalog for custom components. Browsing preferences are transient projections: style selection and interaction-state changes reset the view, while edits and clearing still update only the selected Project Model state. The property list scrolls independently beneath its filters, with the live preview beside it or above it at narrower widths. The page Object Inspector is hidden while Styles is active, restoring its previous visibility when returning to a page.

Visual components share `@webrad/runtime/visual`: property readers, class names, common style projection, and component CSS. React maps canvas-presented registered types to the appropriate design-time DOM element; selection, hit testing, and keyboard behavior remain in the separate design overlay. `WebPopup` uses the same visual style contract at runtime, while its explicit tray presentation keeps it out of that design-time canvas.

Containers own children and `WebPanel` is the first child-capable component. In version 2, a fixed container uses child `bounds`; an align-to-parent container uses item anchors and insets; row and column containers use item sizing, constraints, grow/shrink, gap, wrapping, and alignment. There is no page-level layout mode. Component IDs remain unchanged as a node moves between these layout modes.

Registry `styleEditor.previewProps` supplies optional transient representative property values to the Styles preview, independently of component insertion defaults. Panel uses this to preview border progress enabled at 50 percent while new Panels still start with progress disabled at 0. Preview metadata is cloned/frozen with the definition and never saved as project state.

Panel owns its optional progress overlay as part of the `WebPanel` runtime class. `progressEnabled`, `progressValue` and readonly `progressVisible` are typed in authored page/reusable code. Designer/runtime share pixel-based SVG border geometry and lifecycle observation through `@webrad/runtime/panel-progress`; the overlay is not a model child or an additional component identity. Its dedicated color/track/thickness style fields are scoped to Panel. See [Panel border progress](panel-progress.md).

# Interaction handler arguments

Double-clicking an Interaction generates `(sender, event)` for every registered component event. The sender is the concrete runtime class. Registry `eventType` metadata selects `KeyboardEvent`, `MouseEvent`, `FocusEvent`, `InputEvent` or the default `Event`; `eventDetailType` selects `CustomEvent<T>` instead, retaining registered detail-field constants. Native DOM types and the standard `Error` type require no runtime import. Repeating-row handlers retain their typed `CurrentRow` as the third argument.

Reopening an older method or function property adds missing arguments and strengthens an untyped or generic `Event` parameter through TypeScript AST edits. The authored body, existing parameter names, explicit specialized event types and unrelated source remain intact. No project-format migration is required.
