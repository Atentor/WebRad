# WebRAD architecture

Deploy has a dedicated typed preload capability rather than extending renderer filesystem access. The main process validates every request, requires the trusted IDE frame and current opened project, and binds native directory selections to that project's identity and root. Main-owned directory capabilities persist separately from the Project Model. A destination copied from another machine requires a native selection. Filesystem roots, home/project ancestors, source folders and symbolic links are rejected.

The compiler builds an in-memory deployment artifact containing text and binary files. The main process stages it beside the validated destination, emits request-correlated progress for each actual file, and publishes by directory replacement with rollback. Existing destinations must be empty or belong to the same project with unmodified generated contents; unknown files are preserved by refusing replacement. The ownership manifest also allows obsolete generated files to disappear on the next deployment.

Deployment uses browser ES modules and shared chunks, preserving the project's page, reusable, model and unit organization. Compiler reachability and an AST projection of the central runtime registry remove unused adapters and optional media dependencies; authoring still has the full typed runtime contract. Build/F9 and Debug Preview retain their isolated in-memory script and source-map contracts. Generated code never imports Electron or Node.

PWA generation is a compiler-only concern. Raster icon generation runs in Node through packaged Sharp; browser output has no image-processing dependency. The generated worker uses a content revision and application scope for its cache, waits for old clients before normal updates, and caches only the explicit static artifact set. It never caches authentication/API data. Manifest identity, colors and display settings originate in the Project Model; Preview does not install workers into the IDE's shared preview origin.

Project colors are owned by `settings.colorPalette`, with up to ten named `{ id, name, color }` entries and a default Aurora palette. The renderer projects them through `ProjectColorPaletteContext`; shared pickers write bounded `var(--wr-palette-<id>)` references into existing string color properties and gradient endpoints. Native inputs resolve the current value while preserving that identity; custom edits replace the reference with a literal. Palette buttons remain separate from color-value fields, and `StylesColorPalettePanel` owns configuration with Save/Cancel and Restore Aurora.

The Project Model validates stable identities and all saved references across styles, pages, reusable definitions, and scrollbars. Removing an entry detaches its references at their last value in one project update. Default style creation binds matching Aurora colors through the central style-property metadata. The renderer emits the current variables for the Designer/style previews; the compiler emits the same variables in ordinary browser CSS. Browser-safe runtime style projection supports palette references in every color and gradient candidate without changing typed component color APIs or introducing a Designer/Electron dependency. The old string-array palette shape has no compatibility layer.

The About dialog identifies WebRAD as Powered by Atentor and highlights its website and documentation. Its `links.open(target)` preload API accepts only the typed `atentor` and `webrad` targets. The main process validates the trusted IDE main frame and exactly one allowed target before calling Electron `shell.openExternal` with the corresponding fixed HTTPS address (`https://atentor.com` or `https://webrad.atentor.com`). The renderer has no arbitrary URL-opening or Electron capability; browser-launch failures remain visible in the dialog.

## Direction

Windows installation branding is owned by the Electron main process. For Squirrel installations only, `installation-icon.ts` copies the packaged `resources/Icon.ico` to the installation root's `app.ico` and sets the current user's WebRAD uninstall entry `DisplayIcon` to that local path. It runs during installation, updates, and normal startup to repair older Electron icons, and skips development, portable applications, other platforms, uninstall, and obsolete-version hooks. Forge uses `scripts/windows-installer.nuspectemplate` to omit the legacy `iconUrl` metadata so installation never downloads the Electron icon. Branding failures are logged as `IDE` warnings without blocking application startup.

WebRAD is a desktop IDE built with Electron, React, and web tooling, while projects produced by it are normal browser applications. The versioned Project Model owns all persistent state. The Designer, Object Inspector, Explorer, language services, generator, compiler, and Preview are projections or consumers of that model.

API Client authoring exposes concrete request objects directly as `Client.RequestName.parameter` and `Client.RequestName.execute()`, alongside the `Requests` catalog and active `Operation`/`Request` flow. The client itself exposes `parameter` for its active request and `execute()` overloads for active or named execution. The generated `WebApiClientInstance` type maps configured names to real `WebApiRequest` objects; runtime getters share their stable-ID request cache and follow configuration renames/removals. Client members, object/prototype names and `then` remain protected; conflicting request names use the `Requests` namespace. Browser-only settings accessors validate changes against the component's runtime configuration, maintain stable operation IDs and isolate values by request/instance; they do not modify saved project state. Generated instance types carry output schemas, body/query input names and types, and header names in the page/reusable contract, so native Monaco completion and diagnostics work through both direct and `this` references. API Client ambient declarations are emitted from its TypeScript sources into `api-client-typings.generated.json` by `runtime:sources`; the same check covers browser source snapshots and declaration drift. No runtime dependency on the Designer, Electron or Node is introduced.

The uppercase `Parameter` and `Execute` compatibility members are removed from API clients and request objects. Monaco consumes their canonical runtime declarations directly, without filtering duplicate names. Other user-defined types retain their own members and normal lexical scoping.

```text
Electron main -> typed preload bridge -> React renderer
                                        |-> project model
                                        |-> designer
                                        |-> Monaco/language
                                        `-> compiler preview result

project model -> generated source -> esbuild -> browser-only output
             `-> reusable styles -> Tailwind/PostCSS -> static app.css
             `-> reusable definitions -> runtime instance expansion
```

## Package boundaries

- `packages/project-model`: versioned models, validation, serialization, naming, and immutable update operations.
- `packages/component-registry`: component metadata and registry behavior without React dependencies.
- `packages/components`: React projection of the browser-safe visual contract exported by the runtime.
- `packages/designer`: selection, commands/history, geometry, overlays, and design-time interaction. It may depend on the model and registry, never vice versa.
- `packages/language`: generated declarations and TypeScript AST transformations. User source is preserved.
- `packages/runtime`: browser-only component API, shared visual projection/CSS (including the browser-dialog `WebPopup`), DOM-less nonvisual services, and global working helpers.
- `packages/compiler`: UI-independent validation/generation/build pipeline.
- `apps/ide`: Electron main/preload/renderer. Main owns filesystem, dialogs, processes, and project operations; renderer has no Node access.

Packages are created only when they contain working behavior.

The main process configures `WEBRAD_TAILWIND_BASE_PATH` to the repository root in development and `resources/app.asar` in packaged applications. Both Designer CSS and generated application CSS resolve Tailwind imports from this base, independently of the executable's working directory. Forge copies the PostCSS/Tailwind dependency tree into the archive and unpacks native modules. The packaged smoke launches with the executable directory as its working directory to cover installed-app resolution.

## Security boundary

The RestGo activity opens a project-scoped administration workspace with connection settings, endpoint editing and a published API catalog. The RestGo workspace exclusively edits runtime connection settings in `ProjectSettings.restGo`; the administrative credential is separate main-process state and optional OS-encrypted local profile data. The `restgoAdmin` preload capability accepts only typed catalog, endpoint and publication actions, validates every input with strict schemas and reuses the trusted IDE main-frame check. It builds fixed RestGo management routes, limits response size, applies request timeouts and refuses redirects. Catalog projection excludes database passwords. Preview and generated applications have no access to this capability or credential.

`@webrad/designer` imports published API descriptors into the existing versioned API Client configuration. Component creation and configuration use registry metadata and Designer commands, retaining undo/history, stable IDs and instance typing. The additive `restgo-api-token` and `restgo-public` connection values share the fixed URL/path validation of `restgo-session`. Their browser runtime uses only the application token or anonymous access respectively; session mode retains its JWT-only behavior. Generated runtime sources and Monaco declarations mirror these browser APIs. Server endpoint/publication changes are immediate remote mutations, distinct from the project's local command history.

The browser window uses context isolation, sandboxing, and no Node integration. The preload exposes capability-shaped methods such as `project.open`, `project.save`, `files.read`, and `styles.compile`; it never exposes raw `ipcRenderer`. The style capability accepts only validated project style records and returns CSS for live design-time projection; Tailwind and PostCSS stay in the main process. The main process validates every payload, binds filesystem capabilities to the originating main frame and exact renderer URL, rejects path traversal through links, and revokes roots when a project or window closes. Top-level navigation, redirects, browser-window popups, webviews, and web/device permission requests are denied by default. This does not prevent a generated application from using its own in-document native `<dialog>` through `WebPopup`.

Preview content is served in memory from a dedicated loopback HTTP server on `127.0.0.1` with an ephemeral port, unguessable publication tokens, GET/HEAD-only routes, Host validation, and its own restrictive CSP. Publishing a replacement or closing the owning project/window revokes the previous URL. The iframe uses `allow-same-origin` together with the existing forms/modals/scripts sandbox permissions, preserving its HTTP origin for CORS, browser session storage, and Web Locks. Its port differs from the IDE renderer's port, so generated code cannot read the parent or access its preload bridge. Electron web security stays enabled. API requests use browser `fetch` directly; there is no main-process request proxy.

The packaged IDE also serves only its bundled renderer assets from a separate token-protected loopback HTTP server, instead of `file://`, so API Client tests have a valid HTTP Origin. Static routes validate the Host, decode and constrain paths to the renderer root, reject symlink escapes, and disallow embedding the renderer through `frame-ancestors 'none'`. Development continues to use Vite's HTTP origin. Both local servers close when the IDE quits; neither listens on external interfaces or adds filesystem/network IPC capabilities. Preview storage belongs to the local origin for the current IDE run; deployed applications retain their own hosting origin and normal persistence.

## Startup project restoration

The main process records the last successfully created, opened, or saved project's absolute manifest path in `last-project.json` under Electron's `userData` directory. This application preference has its own versioned format: `{ "formatVersion": 1, "projectFilePath": "<absolute .wrproj path>" }`. It stores only the location; the project files remain the authoritative saved state. Atomic, serialized writes protect the preference from partial writes, and preference failures do not fail project operations. A save completing for a superseded project does not replace the active project's recorded path.

At renderer startup, `ProjectController.restoreLastProject()` invokes the narrow, argument-free `project.restore()` preload capability. The main process validates the trusted renderer, reads and validates the preference, loads the project through the ordinary project-file validator, and grants filesystem access only after a successful load. Missing, invalid, or unavailable preferences or projects return no session so manual creation and opening remain available. Automated smoke runs use an isolated preference directory beside the temporary project fixture and verify restoration after renderer reload without reading or overwriting the user's preference.

The controller caches the restore promise for React StrictMode and ignores a restored session superseded by manual project operations. A restored session activates the usual entry page and starts clean, using saved project files and authored source. Closing a project releases its filesystem capability while retaining its last-opened preference for the next application launch. This application preference does not change the version 2 Project Model or generated browser applications.

## Designer model

The IDE workspace follows the supplied Bubble Designer reference with a 42px top toolbar, a 40px activity rail, a Builder/Responsive sidebar, a central canvas, and a full-height Inspector. Open-document tabs, the selected-component chip, zoom, save state, diagnostic counts, and Preview actions belong to the toolbar. Activity buttons invoke the existing Design, Code, Preview, Project Explorer, Styles, Project Settings, and Output operations. Output starts collapsed and opens for build activity or diagnostics; its dock remains below the compact nonvisual tray in the editor column.

Builder projects the active document's element hierarchy above the Registry-backed assets palette. Hierarchy order comes from the root node and each node's `children`, never from coordinates or component names. The tree, canvas, selected-component chip, and Inspector consume the same ordered stable-ID selection, including explicit root selection. Tree search, keyboard navigation, collapse, and multiselection operate on this projection without copying or rewriting component nodes. A later canvas selection reveals its collapsed ancestors. Palette captions and icons resolve through the central Component Registry.

Responsive provides Default, Tablet (768 px), and Mobile (390 px) preview widths. Default observes the Designer scroll host and fills its available content width, excluding padding and the vertical scrollbar, including when the window, sidebars, or zoom change. Content-sized pages retain their model-owned fit-content behavior. The viewport preset, zoom, sidebar navigation, searches, and collapsed UI sections are ephemeral authoring state; they are not written to the Project Model or browser storage. Responsive layout properties edited in the Inspector remain persisted model properties. The Visual and Interaction Inspector tabs expose registered property and event metadata, with independently collapsible categories. All property edits, including names, continue through model commands and preserve component IDs. This workspace refactor does not change the version 2 persisted format or introduce a separate runtime layout model.

The page surface renders real component DOM from the same browser-safe property projection and CSS used by the generated runtime. Both project the version 2 `ComponentNode.layout` contract while retaining `bounds` for fixed-layout fallback. A separate design overlay owns hit testing, selection handles, marquee selection, drag, and resize. Pure geometry services calculate deltas, snapping, bounds, and multi-selection transforms. Pointer movement may use transient UI state; a command commits the model once at operation completion.

`useDesignerPointerInteraction` owns the synchronous pointer transaction separately from its animation-frame projection. Completion uses the actual release coordinates, including when React has not painted the last movement. A three-screen-pixel threshold distinguishes selection clicks from drag/reorder/resize. Escape, lost capture, window blur, hidden documents, and changes to the editing context cancel without writing model commands. Parent/child selections move only their top-level selected ancestors, and preview geometry uses the same parent constraints as committed commands. `tests/designer-interactions.browser.test.ts` exercises native Chromium gestures, focus, cancellation, nested selection and undo/redo at 50%, 100% and 150% zoom in both IDE themes.

Authored child hosts carry ephemeral `data-designer-parent-id` metadata, including empty Registry-owned containers. The browser-only `designer-host-geometry.ts` measures that host's content origin, borders, scrolling and available dimensions at the current zoom. Drops, drag, keyboard movement and resize use these measurements and the projected selection size, including intrinsic sizing and margins. The workbench persists the already-constrained movement delta rather than constraining it again against saved fallback dimensions; reusable definition internals remain encapsulated. Resize handles appear only for axes whose visible dimensions are controlled by bounds. Flow containers expose trailing edges for those axes; automatic sizing and anchored layouts use Inspector layout controls rather than gestures that would write invisible changes.

Designer history compares each immutable model projection with its current command state once and reuses that result until either changes. Opening an already-bound event is navigation and creates no additional history entry. Native edit commands resolve against the visible workspace and current focus through `workbench-commands.ts`; modal dialogs block both menu commands and F9/F12 shortcuts. Monaco handles its own definition-navigation shortcut before the workbench considers F12.

`WEBRAD_PROJECT_CSS` in `@webrad/runtime/visual` defines the shared 16 px project typography and control colors. The Designer canvas and Styles samples opt in through `wr-project-surface`; generated Preview and application documents use the same class on the body, including floating reusable layers. Page roots also establish these defaults. The IDE's typography and light/dark control variables remain outside this project scope. Shared defaults are in Tailwind's components layer so project utilities, explicit typography, and inherited container styles keep precedence. The real Chromium regression in `tests/style-parity.browser.test.ts` compares Designer DOM with a compiled Preview across IDE themes, viewport presets, and zoom; run it with `WEBRAD_BROWSER_PATH` set to a Chrome, Chromium, or Edge executable.

Reusable styles remain project-level model records with stable IDs. The Styles workspace edits their Tailwind candidate groups, the Inspector offers only styles whose registered target type matches the selected visual component, and the Designer injects debounced CSS compiled through the narrow preload capability. Browser DOM ownership is independent of the component's Designer presentation: `WebPopup` is visual and style-compatible, but is selected from the tray; selecting it opens its centered floating design surface rather than placing its window in page geometry. Generated runtime nodes contain only the resolved static class names, so applications have no dependency on the Project Model or Tailwind compiler. The button-only `Icon` style group keeps content mode and icon placement base-only, while icon color and explicit width/height can vary by interaction state; the individual icon remains an instance property. The Data Grid's base-only `Data Grid Button` group has an equivalent, namespaced content and icon presentation for every embedded button, scoped to its stable cell-button markup so it does not alter the grid root. A browser-safe expanded local SVG catalogue is shared by the IDE, React component projection, generated DOM runtime, and Monaco declarations, so no generated application depends on the Electron renderer or an icon network request. The Inspector presents that catalogue through an accessible visual modal gallery with in-place ID/label search rather than a textual icon dropdown.

`ProjectSettings.scrollbar` is a separate global application-style record rather than a component style or IDE theme preference. Its validated Aurora-default colors, borders, radii, and vertical/horizontal dimensions are compiled into `assets/app.css`; Preview renders that same compiled artifact, so it and a generated build agree without the Designer changing its own chrome scrollbars. The compiler emits the complete WebKit pseudo-element projection, while Firefox progressively receives its supported `scrollbar-color` and closest native thickness. Browser-specific geometry remains browser-owned rather than becoming another mutable Designer state.

DOM-less nonvisual nodes remain children of the page in the Project Model but are projected into a dedicated design-time tray instead of the canvas. Generated classes construct their typed runtime service instances directly from registered properties, immutable IDs, and user-facing names, while the compiler removes those nodes from the page DOM model. Nonvisual runtime objects therefore retain the same identity contract without pretending to own a DOM element: `id` remains stable and `name` reflects the current Project Model name.

`WebPopup` is different: it has `visual: true`, `designerPresentation: "tray"`, and owns visual children. The tray keeps its launcher out of page canvas layout and geometry, but selecting the Popup projects a centered floating editor for the Popup itself and its descendants. That editor uses the ordinary drop, selection, resize, event/code, style, and responsive-container interactions; `layout.container` belongs to the Popup's one inner child host. The Popup is a pure container: it has no caption/message properties or generated header shell, and its compatible `styleId` resolves onto the native-dialog root by the ordinary visual-style pipeline. The Popup window has no persisted page position or layout-item rules, only its width and height. The compiler preserves the normal visual hierarchy in the browser DOM model. Its runtime control wraps a native `<dialog>` element and enters the browser top layer when shown modally. It is therefore a visual runtime container with a tray-based design-time entry point, not a DOM-less service.

Component IDs are immutable. Names are validated TypeScript identifiers unique within a page. Version 2 removes page-level `layoutMode`: each component persists a container mode (`fixed`, `align-to-parent`, `row`, or `column`) plus item sizing, constraints, anchors, and insets. `bounds` remains the deterministic geometry fallback for fixed-size axes. In a fixed container, `stretch` preserves the component's `x`/`y` as its leading offset and uses the matching trailing inset; `fit-content` preserves that leading offset and grows around rendered content rather than shrinking descendants. The shared browser projection uses intrinsic sizing for flow content and observes fixed/anchored child envelopes for dynamic growth, with min/max constraints applied only as bounds. An in-flow reusable definition receives the same intrinsic bootstrapping only until a placement maximum applies; an explicit maximum always caps the definition root as well. The Designer keeps derived sizes local to each physical reusable placement, allowing nested instances of the same template to remain independent. These derived dimensions stay in the projection, never in the model. Runtime and Designer implementations must derive their layout from this shared Project Model contract rather than retaining independent layout state.

## Reusable visual components

Reusable Components follow the same model-first boundary. The project manifest owns a `reusableElements` collection of page-shaped definitions, each with a `WebPanel` root; they are not routes. Each definition has deterministic generated and authored TypeScript companions under `reusables/`, just as pages do under `pages/`. The Registry supplies one visual, childless `WebReusableElement` wrapper type. A wrapper is placed in a page or another definition through its `reusableElementId` property, while the definition remains the sole owner of its child hierarchy. The Designer renders that reference in place, opens the definition with Design, Code, and Preview views, and exposes draggable definitions through Project Explorer. No IDE view reconstructs a reusable by copying its children into the placement node.

The aggregate validator resolves every reference across pages and definitions, requires globally unambiguous page/reusable IDs and portable names, rejects recursive definition graphs, and blocks definition removal while references remain. This validation lives in `packages/project-model`; the Designer, compiler, and runtime consume only validated aggregates. Legacy v2 manifests without the additive collection normalize to `[]` before becoming the canonical in-memory model.

At runtime, `mountPage()` expands definitions after compilation and before DOM construction. The immutable IDs in a definition are template identities only. Each placement gets a physical runtime ID scoped by its own instance ID, including nested placements, so component maps, DOM attributes, and mutable browser objects are isolated even when one definition is mounted repeatedly. The runtime never persists those clones back into the Project Model.

Instance geometry belongs to the `WebReusableElement` wrapper, not the definition. In-flow instances use the normal shared responsive-layout projection. A wrapper with `placement: "floating"` instead projects as a fixed viewport overlay with its own horizontal/vertical viewport anchors, bounds offsets, and z-index; it leaves the shared definition and its layout untouched. The runtime hosts floating instance DOM in a page-owned sibling overlay layer outside the styled page tree, so transforms or clipping on a panel cannot turn the fixed placement into a parent-relative element. The definition root fills the wrapper, which preserves its visual composition at every placement size.

Every physical reusable placement receives its own authored class instance after the page mounts. Its generated class exposes the definition's visual controls (including a tray-authored `WebPopup`), creates any DOM-less nonvisual services, and binds persisted events exactly as a page-generated class does. Event handlers and instance fields are therefore isolated per placement. `this.name` continues to identify the reusable definition root, while readonly `this.pageName` identifies the containing page for inline, nested, and floating placements. Generated code receives an explicit template-to-physical component-ID map, rather than relying on the scoped-ID string format, so an unusual ID collision cannot bind a handler to the wrong element. Definition children remain encapsulated: a host page can address only the wrapper, while the reusable's own authored class addresses its descendants.

## Internal page navigation

The compiler registers every project page, its runtime visual model, and its authored class in one browser-side `WebPageRouter`. An event handler navigates inside the application with `Navigate('PageName')` or the stable page ID. When the destination exactly matches a registered project page, the generated bootstrap swaps the mounted page without reloading the browser: it emits `OnHide`, removes the previous page and its floating layer, disposes generated bindings, mounts the target, and invokes its normal `OnCreate`/`OnShow` lifecycle. Page-local runtime state is therefore recreated on each route activation.

The canonical internal URL is a static-host-safe hash such as `#/PageDetails`. Direct links and browser back/forward events resolve through the same router, with an empty or unknown hash falling back to the project entry page. Destinations that do not match a project page retain `Navigate`'s browser behavior, including external URLs and explicit new-window targets.

## IDE themes

The dark IDE theme uses neutral graphite surfaces inspired by VS Code's classic dark theme: `#1e1e1e` for the workspace and editor, `#252526` for panels, and `#333333` for the toolbar and activity rail. Application chrome colors are centralized in `theme.css`; the Designer stylesheet supplies layout rather than a second color palette. Monaco uses the matching editor, gutter, widget, and selection colors. Theme switching remains transient IDE state and does not rewrite authored component styles or generated application styling.

## Commands and selection

`SelectionManager` owns ordered selected IDs and anchor selection. `CommandHistory` owns executable reversible commands and transactions; it does not store whole-project snapshots per edit. Multi-property edits form one transaction.

## Code and language services

Each user file owns one long-lived Monaco TypeScript model whose URI matches its project path. Models survive Design/Code/Preview switches so undo history, view state, cross-file definitions, references, rename, hover, signature help, formatting, inlay hints, and IntelliSense share one project-wide language-service graph. Model edits are projected back through `ProjectController`; the versioned Project Model and its user-source map remain the source of truth.

The workbench owns model view states rather than the editor wrapper's global cache. It saves and restores cursor, selection, scroll and folding before applying a new navigation request, and releases those states with the project's models. Project-driven source changes use a minimal undoable Monaco edit, preserving unaffected content, CRLF boundaries and Unicode characters. Loading callbacks read the latest project snapshot; asynchronous component completions are discarded when their model/version, metadata or cancellation token has changed. Content subscriptions acknowledge the updated buffer without rescanning other unchanged project models on every keystroke.

Runtime declarations and every generated page declaration are synchronized as disposable TypeScript extra libraries. Stale models and declarations are removed when pages or projects change, while generated implementation files remain separate and replaceable. User files are changed only by explicit editor actions or TypeScript AST transformations. Event generation parses TypeScript, detects the target class/method, inserts a method through compiler AST nodes/printers, and returns both its stable navigation range and a collapsed cursor target inside its body. Monaco reapplies a pending target after asynchronous editor mounting, reveals it, and focuses the handler body.

Every non-root component in a page, visual or nonvisual, becomes a typed `public readonly Name: RuntimeType` field on the generated base class. Authored instance code can use either `Name` or `this.Name`; the root remains `this`. Monaco inserts the bare component name and offers native typed property completion. Generated declarations carry document-specific component metadata. A custom TypeScript worker appends module-local declarations to language-service snapshots only, keeping authored models and diagnostic offsets unchanged. Hidden declarations are excluded from formatting, outline, references, and code fixes; definition navigation targets the actual generated field.

The compiler shares the same AST and symbol-based resolver. It type-checks an in-memory snapshot, then qualifies only unshadowed component references in its browser bundle input. Local variables, parameters, imports, object keys, strings, comments, and existing qualified accesses retain normal TypeScript semantics. Bare references work in instance methods, accessors, field initializers, constructors after `super`, and nested arrow callbacks. Static code, module-level use, nested classes, and ordinary function callbacks report an instance-scope diagnostic. Each reusable placement uses its own receiver; no component globals are emitted or authored files rewritten. Component renaming remains a Designer action.

Instance-method parameter defaults and destructuring defaults use that same receiver. Block-scoped loop and catch bindings shadow components only in their lexical scope; module-level `var` retains normal module binding semantics. The TypeScript worker retains at most 32 document snapshots and scope records, keyed by source/declaration versions and invalidated when metadata disappears. Both bare and `this.Name` component-field renames are rejected by Monaco so the Project Model remains authoritative; ordinary local-symbol renames still work.

For the registered MVP component set, Registry metadata and runtime declarations constitute one typed authoring contract: properties exposed by the Registry have corresponding runtime accessors on their component type, so completion after `this.Name.` reflects the API that executes in Preview. Renaming a component regenerates the field and declarations but deliberately does not rewrite user-authored TypeScript automatically. Existing references to the old name remain visible compiler diagnostics until the author updates them.

Monaco reports syntax, suggestion, and semantic markers continuously for fast feedback. The Problems projection merges and deduplicates those markers with the last authoritative compiler result, preserves source/code/range metadata, and navigates either to source code or the affected model component. The standalone F9 compiler remains authoritative because the embedded Monaco TypeScript service and the build compiler can be different patch versions.

The editor's JetBrains Mono Light face is self-hosted from the pinned `@fontsource/jetbrains-mono` package. Vite emits the weight-300 normal and italic webfont assets into the renderer bundle, and the renderer CSP permits only the packaged self origin. Monaco therefore has identical typography in development and installed applications without a system font or CDN dependency. The Electron package also carries `JetBrainsMono-OFL.txt` beside its resources so every distributed copy includes the font copyright and SIL Open Font License 1.1.

## Cross-platform decisions

Filesystem paths remain native inside Electron and are converted to URI/path forms at boundaries. Build logic is a Node API rather than shell scripts so Windows and Linux share behavior. Runtime and compiler output contain no Electron imports.

## RestGO integration

`WebFileUpload` is a registered nonvisual `WebNonvisualComponent` service with `OpenFile()` and `SendToRestGO()` methods. It owns a hidden native chooser only while selecting, returns name/available relative path/byte size/extension, and keeps browser `File` objects and request state local to each instance. The existing component-property model persists only the filter, enabled state and default visibility. Upload results preserve all RestGO Storage metadata and add an absolute URL retaining the connection prefix; private-file authorization is unchanged. Registry-owned `OnProgress` metadata scaffolds typed percentage/byte fields in Monaco so authored code can update other components. The shared SDK measures actual cross-origin XHR upload progress with credentials disabled; same-origin/unsupported/custom-fetch calls retain cookie-omitting fetch and indeterminate progress. XHR can follow redirects before final-URL rejection, so configured instance URLs must be final. Generated page/reusable classes construct nonvisual services from saved properties and dispose them with their scope, cancelling chooser/upload state and event subscriptions. No visual rendering or style is emitted for File Upload.

`RestGoClient.CurrentUser` projects the SDK's last server-confirmed identity as a readonly, frozen snapshot with `nome`, `email`, `id`, `emailconfirmed`, and `ativo`. The authentication service owns the projection, so shared runtime and standalone clients follow the same login, restoration, refresh, validation and termination state. Reads do not issue requests, expose credentials, trust persisted identity, or assert current server validity. The value is null before successful restoration, without a session, and after disposal; transient errors preserve confirmed identity. Existing `getUser()` remains the server-validation API.

`WebApiClient` can opt into the additive `connection: 'restgo-session'` component configuration. The runtime resolves the shared RestGO client for every request, pins the URL to its configured origin and base path, validates/renews the current SDK session, and supplies its Bearer JWT. It refuses anonymous requests and raw API-token fallback. Callers cannot change the base, escape the endpoint prefix, replace Authorization, or follow redirects. Endpoint HTTP failures retain the existing API Client errors and lifecycle events without automatically replaying a write operation.

The IDE projects this connection through a read-only integration URL and separate request-setting tabs. `packages/designer` builds browser test requests from the Project Model; a transient JWT source can use the runtime's public request-preparation helper. Neither the test JWT, chosen upload files, nor sampled response bodies enter the persisted configuration. Multipart text fields use URL-encoded configuration content, while native files are supplied as runtime `FormData` overrides. Existing client configurations without a connection continue to use their authored base URL.

The Registry also exposes `OnUnauthenticated`, scaffolded through the same AST generator with a `WebPage` sender and no user payload. The bridge reports confirmed anonymous entry and authoritative session termination once per anonymous period, resetting after authentication or a new shown-page observation. Each client has one ref-counted browser monitor, with validation every 30 seconds while visible and on focus/visibility restoration; concurrent requests share the SDK validation. The initial notification performs a fresh server check rather than treating a null initial identity following a network failure as proof of logout. Revision checks suppress an old anonymous result after a newer auth notification. Hidden/disposed pages cancel notifications, and the last observer removes the timer and focus/visibility listeners. Disabled integration and transient failures never emit anonymous state. Existing event-map persistence needs no schema change.

The WebPage Registry definition exposes `OnLogin` and `OnLogout` under Interaction's RestGO category. Metadata selects public `WebPageLoginEventDetail`/`WebPageLogoutEventDetail` types and a `user` destructuring scaffold through the existing TypeScript AST handler generator. Bindings use the existing root event map; no project schema change is required. Shown pages observe the shared SDK and release their subscriptions on hide, close, or disposal. Mounted reusable authored scopes with root auth bindings release them on disposal. Notifications are queued outside the SDK callback iteration so handlers can navigate safely. Login delivers the current user once on restoration or a successful login; token renewal and same-user validation update identity without repeating login. Logout delivers the last authenticated identity on authoritative termination. DOM payloads contain user identity and a login restoration flag, never access or refresh credentials. Page fields remain instance-local, and `RestGO.getUser()` provides a fresh server-validated identity for other handlers.

`packages/restgo-sdk` owns the browser-safe TypeScript client for the documented RestGO user authentication, Storage, and versioned dynamic API contracts. It depends on browser APIs rather than Electron, Node, React, or the Designer. It can also be imported independently through its public package export.

The versioned Project Model owns `settings.restGo`, including the enable flag, instance base URL, optional application `apiToken`, API version, default database, and session persistence policy. The single **RestGo integration** section edits one transactional draft and the normal project save persists that configuration to disk. The application token is emitted to Preview and generated browser code, so it must be appropriate for client access. User JWTs and transient request results are runtime state rather than project settings. Administrative credentials are not part of the native project configuration.

The browser runtime owns the shared `RestGO` client. The compiler configures it from the validated model before constructing pages and starting the router, so page navigation shares one authentication state. Both the runtime import and the generated global resolve to the same client. Access while the integration is disabled fails with a clear configuration error.

The shared transport selects the raw application token for automatic dynamic API requests without a session and `Bearer <JWT>` with a session. Signup and login explicitly select `auth: 'none'`, omitting `Authorization` even when an API token or JWT is available. Signup does not require a configured token, wait for session renewal, or start a session; the server must allow anonymous common-user registration. A rejected signup or login does not revalidate or clear the existing session. Logout returns automatic dynamic calls to the application token. Explicit dynamic credential modes, other public endpoints, and refresh preserve their endpoint contracts; no automatic credential-type fallback occurs after rejection.

The SDK client exposes positional `login(email, password, remember = false)` and direct `logout`, `getSession`, `getUser`, `refreshSession`, and `onAuthStateChange` methods for event code. They delegate to the same authentication service and preserve typed `{ data, error }` results, session lifecycle, and event subscriptions. Routing and presentation remain responsibilities of authored code. These methods are available through the shared facade and independent SDK clients, without additional globals or persisted settings.

Authentication renews JWTs through the public `POST /auth/refresh` contract using only the opaque refresh token in the body. Single-use rotation shares one in-flight operation within a client and uses the browser Web Locks API across local-storage clients/tabs. It rereads stored credentials after acquiring the lock, persists the entire rotated pair atomically, and never treats a cached user identity as authoritative. Local shared sessions require Web Locks in a secure context; isolated session/memory storage has a realm-local queue. Network/429/5xx failures retain credentials with bounded exponential retry intervals and `Retry-After`; refresh 401 clears the session. Protected requests retry once only after rejection with 401 and successful renewal; mutations are never replayed for transient transport errors. Dynamic endpoint 401 first checks `/auth/session` to preserve credential-mode errors.

Browser timers renew before expiry; requests and initial restoration also recover an expired JWT. `TOKEN_REFRESHED` exposes the returned identity and new credentials to subscribers. Logout waits for an in-flight rotation and revokes the resulting session token under the same lock. Authentication generation checks prevent older responses from replacing a newer login/logout. Reconfiguring the runtime disposes the previous client's timers/listeners; disposal preserves credentials and an already completed rotation without revoking the server session.

The runtime source synchronization check also detects drift in SDK sources and declarations.

The main process checks the trusted frame and opened-project capability before and after the native picker; the renderer cannot supply an external asset path.
