# Project format

Every persisted structure carries `formatVersion`. The current Page-based format is version 2, uses UTF-8 JSON, and separates visual state from TypeScript source.

```text
MyProject/
  MyProject.wrproj
  pages/
    PageMain.wrpage
    PageMain.generated.ts
    PageMain.ts
  assets/
    images/
    styles/
  models/
  units/
```

The `.wrproj` manifest contains the project ID, display name, entry page ID, page descriptors, reusable component styles, and settings. A `.wrpage` contains page metadata and component nodes. Component and style references use immutable IDs; names are user-facing labels and are not identities.

Version 2 removes the page-level `layoutMode`. Each `ComponentNode` instead has a required `layout` object, so the same node declares both how it lays out direct children and how it participates in its parent. `layout.container` contains `mode` (`fixed`, `align-to-parent`, `row`, or `column`), four numeric paddings, `gap`, `wrap`, `justifyContent`, and `alignItems`. `layout.item` contains width and height modes (`fixed`, `stretch`, or `fit-content`), minimum/maximum dimensions, `grow`, `shrink`, horizontal and vertical anchors, and `left`, `right`, `top`, and `bottom` insets. Maximum dimensions are either a non-negative number or `null`; padding, gap, minimum dimensions, and grow are finite non-negative numbers. Insets are finite numbers.

New nodes use a fixed container with zero padding and gap, no wrapping, and `start` alignment. Their item defaults to fixed width and height, zero minimums and insets, `null` maximums, zero grow, shrink enabled, and `start` anchors. `bounds` remains persisted as the fixed-layout fallback (`x`, `y`, `width`, and `height`); it is not a second responsive layout mode.

Reusable styles are stored inline in the manifest as `styles: ComponentStyleModel[]`. Each style has an immutable `id`, a project-unique `name`, one compatible `componentType`, an optional `preset`, and five structured property maps under `states`: `base`, `hover`, `focus`, `active`, and `disabled`. Every state is always present, even when empty. `preset: "default"` identifies a protected built-in default; a project may contain at most one such style for any component type. Its name and state maps can be customized, but its preset and component type cannot change and it cannot be deleted. Values are typed enums, bounded numbers, validated hexadecimal colors, numeric lengths with an explicit `px`, `rem`, `%`, `vw`, or `vh` unit, or a bounded gradient object. A component optionally stores `styleId` in its `.wrpage` node, allowing any number of compatible components to share the same style.

`WebButton` styles collect their icon controls in the `Icon` editor group. The base-state-only presentation properties are `buttonContentMode` (`text`, `text-icon`, or `icon`) and `buttonIconPosition` (`left`, `right`, `top`, or `bottom`); changing a button's content structure on hover or focus would be unstable. `buttonIconColor` and `buttonIconSize` are `WebButton`-only properties available in every style state. Color defaults to `current`, so the icon inherits the text color until overridden; size is an explicit non-negative `px` or `rem` length and defaults to `16px`. The component node owns its individual `icon` prop, selected from the local SVG catalogue shared with the IDE chrome; it defaults to `add` and can be changed independently even when several buttons share a style. The visual picker searches by icon ID or label before selection, and includes authentication and entrance/exit variants such as `login`, `logout`, `door-in`, and `door-out`. New projects set the Default Button presentation to text and icon with a left 16px icon, and icon-only buttons retain their caption as their accessible name.

`textGradient`, `backgroundGradient`, and `borderGradient` share one safe two-color linear-gradient value: `{ "kind": "linear", "direction": "to-right", "from": "#2563eb", "to": "#7c3aed" }`. Its direction must be one of the eight compass directions from `to-right` through `to-top-right`, and both endpoint colors must be six-digit hexadecimal values. Background and border gradients produce static CSS utilities; text gradients target the component's caption element, preserving its background paint. A border gradient is rendered as two background layers — an inner fill clipped to the padding box and the gradient clipped to the border box — over a transparent solid border. This respects the configured border width and radius on native controls as well as ordinary elements, unlike `border-image`. Text gradients are available to labels, buttons, and checkbox captions. Within one state, each gradient is mutually exclusive with its same-target solid color (`textColor`, `backgroundColor`, or `borderColor`), preventing redundant declarations.

The metadata-driven style editor and compiler share one pure property-to-utility generator; users never need to author Tailwind class strings. The compiler converts saved values into exact Tailwind candidates and automatically applies the appropriate variants to `hover`, `focus`, `active`, and `disabled`. Focus also targets compound controls through `focus-within`, while disabled targets native `:disabled` and the common `aria-disabled` root contract. Tailwind source discovery is disabled, so generated CSS contains only the project catalog's candidates plus Tailwind theme variables. Preflight is intentionally omitted to preserve WebRAD component semantics. Generated applications receive static CSS and have no Tailwind runtime dependency.

The reusable-style property catalog covers CSS layout and alignment, dimensions, spacing, typography, button icon presentation, color, and size, solid colors and safe two-color linear gradients for text/background/border, borders and focus rings, effects and filters, transforms, transitions, basic built-in animations, interaction, and image fitting. It is distinct from the structural v2 `ComponentNode.layout` contract, which controls responsive container and item behavior. The editor metadata supplies labels, categories, controls, options, applicability, descriptions, and valid defaults. Arbitrary user code, selectors, class lists, raw CSS gradients, and custom keyframes are intentionally outside this format; this keeps persisted candidates bounded, statically compilable, and safe from Tailwind source expansion.

Page documents can be parsed and edited independently while retaining a `styleId`. Cross-document rules are enforced when the aggregate is assembled or saved: style IDs and case-insensitive names must be unique, every component reference must exist, and the style's `componentType` must exactly match the node type. Removing a user-created style through the project-model helper atomically removes it and clears all component references; protected default styles instead remain available for future visual insertion. Component IDs and unrelated style IDs remain unchanged.

Readers validate the complete document before it enters the model. Only the current version 2 Page schema is accepted; version 1, incompatible, legacy-shaped, and unknown future documents are rejected instead of migrated. `styles` is required in version 2 manifests and aggregates. New projects initialize it with the ten visual Aurora defaults, each marked `preset: "default"`; an existing valid version 2 project can omit presets and preserve its current library unchanged. Serialization is deterministic, including the `preset` and `layout` field order, so source-control diffs remain useful.

Generated `.generated.ts` files are replaced atomically. User-authored `.ts` files are changed only from explicit editor state, never by generation; an unowned file collision is rejected instead of overwritten. Page names and descriptor paths are canonical and portable across case-insensitive filesystems.

Saves are serialized per project root. Artifact writes have rollback snapshots, the manifest is the commit point after all referenced files exist, and retired or path-reused artifacts are copied to `.webrad/trash/<timestamp>-<id>/` before replacement. A small `.webrad/pending-cleanup.json` journal makes post-commit removal retryable after interruption.
